# Source Code Analysis Persistence Rule / ソースコード解析結果の永続化ルール

## 目的 (Purpose)
ソースコード全体の再解析によるトークン消費と処理コストを最小化するため、解析・修正によって得られた知識を `CODE_ANALYSIS.md`（`.agents/references/CODE_ANALYSIS.md`）に永続化し、以後の開発作業で再利用する。

---

## 最重要原則 (Core Cardinal Rules)
1. **再解析前の参照義務 (Mandatory Prior Reference)**:
   ソースコードを一から再解析する前に、**必ず `CODE_ANALYSIS.md` を参照すること**。
2. **コンパクトで再利用可能な知識の維持 (Token-Efficient Knowledge)**:
   後続のAIエージェントがソースコード全体を再解析せずに作業を開始できるよう、コンパクトで再利用可能な知識として維持すること。
3. **コスト最小化の追求 (Minimal Reading Cost)**:
   網羅性そのものを目的とせず、開発作業に必要な情報を最小の読み取りコストで取得できる状態を維持すること。

---

## 基本ルール (Standard Rules)

### 1. 解析結果の記録と再利用
- ソースコードを解析した場合、その結果を `CODE_ANALYSIS.md` に記録すること。
- ソースコードを修正した場合、修正によって影響を受けた解析情報を更新すること。
- 既存の解析結果がある場合は、作業開始時に最初に読み取り、再利用すること。
- 既存の解析結果とソースコードの整合性が確認できる場合、同じ内容を再解析しないこと。
- 解析結果が古くなった場合や不整合が判明した場合は、影響範囲に限定して再解析・更新すること。

### 2. 解析コストの最小化
- `CODE_ANALYSIS.md` を読むコストが、対象ソースコードを一から解析するコストよりも確実に小さくなるように記述すること。
- ソースコード全体を再読込・再解析する必要がないよう、後続の開発作業に必要な情報（判定境界、引数仕様、ライフサイクル、状態遷移など）を優先して記録すること。
- 変更のたびにソースコード全体を再解析せず、変更箇所とその依存関係を中心に差分解析すること。
- ソースコードから容易に再取得できる自明なコード列挙や、開発作業に寄与しない不要な説明は記録しないこと。

### 3. AIによる読み取りに最適化した形式
- 人間向けの散文よりも、**AIが少ないトークンで正確に解釈・再利用できる構造化形式（Compact Structured Format）**を最優先すること。
- 冗長な文章、重複説明、一般論、不要な背景説明は排除すること。
- Markdownの見出し、箇条書き、決定表（Decision Tables）、キー・値ペア、Mermaid状態遷移図を活用し、情報を極力簡潔に整理すること。
- ファイルパス、シンボル名、関数名、クラス名、依存関係、制約条件、影響範囲などは、具体的かつ簡潔に記述すること。
- 曖昧な表現を避け、推測の余地なく後続タスクに直結する正確な情報を記録すること。
- 同一情報の重複記載を避け、既存の項目をインプレースで更新すること。

### 4. 記録する情報
対象に応じて、後続作業に必要な情報を選択して記録する：
- **構成**: 主要モジュール、クラス、状態変数の役割
- **依存関係**: モジュール間の依存、呼び出し順序、データの流れ
- **設計・仕様**: コアロジック、判定閾値、暗黙の制約、不変条件（Invariants）
- **状態遷移**: ライフサイクル状態（`st_init`, `st_pressing`, `st_processed` 等）とトリガー
- **変更影響範囲**: 機能を変更した場合に確認・修正すべき波及箇所
- **既知の課題**: 確認済みの問題、潜在的リスク、破壊的変更につながる条件
- **検証方法**: 関連する回帰テスト、実行コマンド
- **解析状態**: 解析済みの範囲、要再確認・未検証の項目

### 5. 修正時の更新手順
1. `CODE_ANALYSIS.md` を読み、既存の解析情報を確認する。
2. 既存情報を利用して、変更対象とその依存関係を特定する。
3. 必要な差分範囲だけソースコードを精査・解析する。
4. ソースコードを修正し、テスト・構文検証を実施する。
5. 変更によって影響を受けた解析情報のみを `CODE_ANALYSIS.md` に反映する。
6. 解析結果と実際のソースコードに矛盾がないことを確認する。

### 6. 正確性と鮮度の維持
- 必ず実際のソースコードを根拠とすること。未確認の仮説を確定事項として記録しないこと。
- 解析結果とソースコードの整合性が不明な場合は「要検証」と明記すること。
- 古くなった情報は更新または削除し、矛盾する記述を残さないこと。
- 変更していない領域については、既存の解析結果を維持すること。
